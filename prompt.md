# Aegis — Implementation Batch 1: Repository Foundation + ShopSim V0

You are working inside a new repository for a master's-level computer science portfolio project named **Aegis**.

Before making changes, inspect the repository, current Git branch, Git remote, and available development environment. Do not assume files exist if they do not. Do not commit, push, merge, create a pull request, or change branches. The human developer will review all changes before performing Git operations.

## 1. Project context

Aegis is a **Distributed Resilience Intelligence Platform**.

The eventual platform will observe distributed applications using telemetry such as metrics, logs, distributed traces, service events, and deployments. It will detect abnormal system behavior, reconstruct service dependencies and failure propagation, rank likely root causes, use a tool-using AI investigator to gather structured evidence, and evaluate its conclusions against controlled faults generated by a component called ChaosBench.

This batch does NOT implement the Aegis monitoring platform yet.

We first need a small distributed application for Aegis to monitor.

That application is called **ShopSim**.

ShopSim is a controlled test environment, not the primary portfolio product.

The eventual initial topology is:

Client
→ Checkout Service
→ Payment Service
→ PostgreSQL

and

Checkout Service
→ Inventory Service
→ Redis

However, PostgreSQL and Redis are intentionally NOT part of this implementation batch.

The purpose of Batch 1 is to establish a minimal but real distributed application in which three independent services communicate across network boundaries.

## 2. Architecture decisions already made

Preserve these decisions unless a genuine technical blocker is discovered.

### Repository

Aegis uses a **monorepo**: related applications, infrastructure, documentation, and later ML/frontend components will live in one Git repository.

Do not create large numbers of empty directories for future systems that do not exist yet.

### ShopSim language

Checkout, Payment, and Inventory will initially be implemented in **Go**.

Do not introduce Python, Node.js, TypeScript, Java, Rust, or another language for ShopSim.

Use the Go standard library whenever reasonable for this first batch. Avoid unnecessary frameworks.

Use Go 1.27.x, preferably the current supported 1.27 release available in the environment. If the local environment cannot support that version, report the issue instead of silently making a major version decision.

### Service communication

ShopSim services communicate synchronously using **HTTP with JSON payloads**.

Do not introduce gRPC, GraphQL, Kafka, RabbitMQ, asynchronous messaging, or another communication mechanism.

### Local runtime

The distributed environment should run using **Docker Compose**.

Each service remains a normal Go application whose language dependencies are managed by Go. Docker packages and runs the services; Docker does not replace Go's own build/dependency system.

### Hardware constraint

Local development must remain practical on a laptop with approximately **16 GB system RAM**.

Keep this first implementation lightweight.

## 3. Batch objective

At the end of this batch, the following distributed request path must work:

Client
→ Checkout Service
→ Inventory Service
→ Payment Service
→ response returned to Client

Checkout must make real HTTP requests to the independently running downstream services.

Do not simulate those downstream calls by importing Payment or Inventory functions into Checkout.

The network/service boundary is a core learning objective.

## 6. ShopSim API design

Implement three independently executable HTTP services:

### Checkout Service

The Checkout service is the public ShopSim entry point.

Expose:

GET /healthz

and:

POST /checkout

Use a minimal JSON request similar in meaning to:

{
"order_id": "order-123",
"sku": "sku-001",
"quantity": 1,
"amount_cents": 2500
}

Perform reasonable validation for required fields and invalid values.

When a valid checkout request arrives:

1. Checkout sends an HTTP request to Inventory to reserve the requested quantity.
2. If Inventory succeeds, Checkout sends an HTTP request to Payment to perform a mock charge.
3. If both succeed, Checkout returns a successful JSON response containing enough information to show that both downstream operations succeeded.

Keep this sequential for V0. Do not add concurrency yet. We may intentionally introduce concurrent downstream calls later as a separate engineering lesson.

Checkout must obtain downstream service URLs through environment variables or equivalent runtime configuration rather than hardcoding Docker-specific addresses directly into business logic.

Use explicit HTTP client timeouts so a failed downstream service cannot cause Checkout to wait forever.

Handle malformed JSON, invalid requests, downstream connection failures, downstream non-success responses, and timeouts with reasonable HTTP status codes and JSON errors.

Do not overbuild a production ecommerce system.

### Inventory Service

Expose:

GET /healthz

and:

POST /reserve

It should accept the minimum information needed to represent:

order ID
SKU
quantity

For Batch 1, return a deterministic mock reservation result.

There is no Redis yet.

Do not implement a complex inventory database or in-memory inventory engine.

### Payment Service

Expose:

GET /healthz

and:

POST /charge

It should accept the minimum information needed to represent:

order ID
amount in cents

For Batch 1, return a deterministic mock payment result.

There is no PostgreSQL yet.

Do not implement real payment processing.

## 7. Ports and Docker networking

Prefer a simple consistent container design.

For example, each service may listen internally on port 8080 while Docker Compose exposes distinct host ports such as:

Checkout: localhost:8080
Payment: localhost:8081
Inventory: localhost:8082

Within the Compose network, Checkout should address downstream containers using Docker Compose service DNS names rather than localhost.

For example, conceptually:

http://payment:8080
http://inventory:8080

Do not blindly use these values if the actual configuration requires something different, but preserve the principle.

This distinction matters:

`localhost` from inside the Checkout container refers to the Checkout container itself, not the Payment or Inventory container.

Configure downstream URLs using environment variables supplied by Docker Compose.
